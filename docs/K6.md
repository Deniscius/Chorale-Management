# Tests de charge k6

## Périmètre et prérequis

Le script `tests/performance/chorale.js` utilise k6, sans dépendance distante. Il cible exclusivement HTTP sur localhost/127.0.0.1. Les données métier ne sont pas modifiées : seuls la connexion, les lectures et l’état des composants Livewire sont exercés. Les sessions et caches applicatifs sont naturellement mis à jour.

Préparer une copie PostgreSQL de démonstration avec des données fictives, les ressources Vite compilées, les caches Laravel de configuration/vues préparés et un serveur capable de traiter des requêtes concurrentes (Apache/PHP, ou Nginx/PHP-FPM). Le serveur `php -S` Windows ne fournit pas une mesure de concurrence représentative. Ne pas utiliser de données réelles ni publier ce serveur local sur le réseau.

Installer k6 depuis les distributions officielles Grafana et vérifier l’empreinte du téléchargement. Fournir un compte administrateur de test via `K6_USERNAME` et son mot de passe via `K6_PASSWORD`. Les identifiants ne doivent pas être placés dans le dépôt ni dans les rapports.

## Exécution PowerShell

```powershell
$env:BASE_URL = 'http://127.0.0.1:8002'
$env:K6_USERNAME = 'demo.admin'
# Définir K6_PASSWORD dans l’environnement local, hors du dépôt.
$env:PROFILE = 'smoke'
$env:SUMMARY_PATH = 'k6-smoke.json'
k6 run --no-usage-report tests/performance/chorale.js

$env:PROFILE = 'load'
$env:SUMMARY_PATH = 'k6-load.json'
k6 run --no-usage-report tests/performance/chorale.js
```

- `smoke` : un utilisateur, visite des vingt écrans principaux, filtre des membres, réinitialisation Livewire et ouverture du formulaire de choriste sans enregistrement.
- `load` : 1 utilisateur pendant 15 s, montée à 5 en 20 s, à 10 en 25 s, puis descente en 10 s. Chaque utilisateur possède sa propre session ; la connexion est effectuée une seule fois par utilisateur. Pause de lecture entre les requêtes. Des réinitialisations de filtres Livewire sont incluses.
- `privacy` : six comptes fictifs distincts contrôlent les pièces privées de liturgie et du secrétariat ainsi qu’un document partagé ; un visiteur déconnecté doit être redirigé vers la connexion.
- `stress` : montée progressive jusqu’à 50 utilisateurs virtuels, avec des paliers prolongés et une phase de récupération. Les vingt écrans et les réinitialisations Livewire sont parcourus avec une pause de lecture ; chaque utilisateur virtuel ouvre une session distincte du même compte de test.

## Montée en charge prolongée

Après un passage `smoke` réussi pour préchauffer tous les parcours :

```powershell
$env:PROFILE = 'stress'
$env:SUMMARY_PATH = 'k6-stress.json'
k6 run --no-usage-report tests/performance/chorale.js
```

Le plan partagé `tests/performance/stress-plan.js` dure 355 secondes, hors délai de terminaison des itérations en cours (15 secondes maximum).

| Étape | Transition | Palier |
| --- | --- | --- |
| 5 utilisateurs | 15 s | 30 s |
| 10 utilisateurs | 15 s | 45 s |
| 20 utilisateurs | 20 s | 45 s |
| 30 utilisateurs | 20 s | 45 s |
| 50 utilisateurs | 20 s | 45 s |
| Récupération à 5 | 15 s | 30 s |
| Arrêt à 0 | 10 s | — |

Chaque palier possède ses propres mesures de durée des pages, erreurs HTTP et compteurs de requêtes. La phase d’une page est celle du début de sa requête. Les compteurs doivent être non nuls pour éviter de valider un palier non atteint. La valeur `rate` des compteurs dans le résumé est normalisée sur toute l’exécution ; pour estimer le débit d’un palier entièrement effectué, diviser son compteur par sa durée.

Les seuils ordinaires restent inchangés : p95 des pages inférieur à 1,5 s et erreurs HTTP inférieures à 1 % pour chaque palier. Deux protections interrompent automatiquement le test si le taux global d’erreurs atteint 5 % après 60 secondes, ou si le p99 HTTP atteint 10 secondes après 90 secondes. Ces protections ne remplacent pas les critères de réussite, plus stricts. Un arrêt anticipé impose de signaler les étapes non atteintes.

Comparer le premier palier à 5 avec la récupération à 5, et conserver les résultats de chaque palier, même en cas d’échec global. Un plateau conforme sur une petite base locale ne détermine pas à lui seul une capacité maximale de production. Le générateur et le serveur partagent ici la même machine ; les données, le cache, la durée des paliers et les ressources de l’hébergement influencent les résultats.

La confidentialité nécessite les comptes désignés dans l’interface : `demo.liturgie` / `demo.associe`, `demo.secretariat` / `demo.associe.courriers`, ainsi que `demo.admin` et `demo.choriste`. Ces comptes de démonstration utilisent ici le même mot de passe transmis par l’environnement. Fournir les identifiants de fichiers fictifs existants :

```powershell
$env:PROFILE = 'privacy'
$env:LIT_PRIVATE_ID = 'ID_DU_DOCUMENT_PRIVE_LITURGIE'
$env:MAIL_PRIVATE_ID = 'ID_DU_DOCUMENT_PRIVE_COURRIER'
$env:SHARED_ID = 'ID_DU_DOCUMENT_PARTAGE_LITURGIE'
$env:SUMMARY_PATH = 'k6-privacy.json'
k6 run --no-usage-report tests/performance/chorale.js
```

Le contrôle vérifie notamment qu’un administrateur non désigné ne peut pas télécharger les fichiers privés. Les réponses 403 attendues sont comptabilisées comme succès de la politique de confidentialité, pas comme erreurs HTTP imprévues. Les redirections sont désactivées pour ne pas confondre une page de connexion avec une page authentifiée.

## Seuils et interprétation

Les seuils de départ sont : 100 % de contrôles réussis, moins de 1 % d’erreurs HTTP inattendues, p95 des pages inférieur à 1,5 s et p95 HTTP global inférieur à 2 s. Chaque écran dispose aussi d’un seuil p95 dans le profil de charge. Un dépassement rend l’exécution non conforme ; les seuils ne sont pas relevés pour faire passer une mesure.

Conserver le résumé JSON et noter : révision, serveur, configuration PHP/OPcache, volumes de données, durée, concurrence et état chaud/froid du cache. Une mesure sur une petite base locale et une montée à 10 utilisateurs ne prouve pas la capacité de production ni la résistance à une charge soutenue.

Ces tests utilisent HTTP et Livewire côté serveur. Ils ne mesurent pas le rendu JavaScript, le temps d’affichage visuel, les transferts de gros fichiers, les écritures métier concurrentes ou les fournisseurs SMS/mail/IA. Ces parcours nécessitent des scénarios séparés sur une base de test dédiée.

## Configuration Windows observée

Sur Apache Windows/PHP 8.2.12, OPcache a réduit le temps de réponse, mais son JIT implicite a provoqué des erreurs VirtualProtect sous concurrence. La configuration de test retient OPcache actif, opcache.jit=off et opcache.jit_buffer_size=0. Une configuration Laravel mise en cache évite aussi les erreurs de chargement de clé applicative observées sur le serveur multithread. Ces réglages concernent le banc local ; ils ne sont pas appliqués automatiquement à un hébergement.
